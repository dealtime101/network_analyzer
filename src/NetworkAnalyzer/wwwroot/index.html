          Protocole pour capturer votre prochain épisode de lag

          1. Quand vous êtes à l'ordinateur, sur la connexion habituelle, démarrez une surveillance de 30 minutes (onglet Surveillance). Indiquez votre serveur de jeu en destination personnalisée si vous le connaissez.
          2. Jouez / travaillez normalement. Au premier ressenti de lag, cliquez « Je lag maintenant » (une fois par épisode, même plusieurs fois par session).
          3. Notez à côté : quoi (jeu, appel, page web), Wi‑Fi ou câble, les autres personnes/appareils qui utilisaient Internet.
          4. Quand la session est finie, ouvrez Diagnostic : lisez l'hypothèse principale, ses preuves, ses limites et le « prochain test utile ».
          5. Si le lag n'est pas survenu pendant la session, recommencez un autre jour/heure : sans épisode capturé, l'outil ne peut rien affirmer.
          6. Faites ensuite un test de saturation (hors période de lag) en Wi‑Fi puis en Ethernet.
          7. Exportez le rapport HTML (et le CSV/JSON si besoin) pour le conserver ou le montrer à votre fournisseur.

          Définitions

          • Médiane : valeur centrale des temps de réponse reçus.
          • p95 : 95 % des réponses sont plus rapides que cette valeur.
          • Perte : requêtes sans réponse ÷ requêtes envoyées. Une mise en veille n'est pas comptée comme perte.
          • Gigue (jitter) : moyenne de |RTT(i) − RTT(i−1)| entre deux réponses consécutives (une perte interrompt la chaîne).
          • Bufferbloat : hausse de latence quand la ligne est chargée, due à de trop longues files d'attente (modem, routeur).
          • QoS de priorisation ≠ SQM : la priorisation ordonne les paquets ; la gestion de file (SQM : fq_codel, CAKE…) empêche les files de grossir. Votre modèle n'en a pas forcément.

          Ce que l'outil ne peut pas savoir

          • Une perte de ping n'est pas toujours une vraie perte (routeurs qui répondent peu aux pings) ; une perte sur un saut intermédiaire d'un traceroute sans perte à destination n'est pas une perte réelle.
          • Le trafic mesuré est celui de cet ordinateur, pas de toute la maison ; aucun programme coupable n'est désigné.
          • Les interférences radio ne sont pas mesurées ; seuls le signal, le canal, les débits de liaison et les voisins Wi‑Fi visibles sont lus.
          • Le jeu peut lagger sans problème réseau (ordinateur surchargé, serveur) : l'outil le dit quand le réseau est sain pendant votre signalement.

          Confidentialité et droits

          • Tout reste sur cet ordinateur (dossier de données). Le seul trafic externe : les pings/DNS vers les cibles et, uniquement à votre demande, le test de saturation.
          • Aucun contenu de communication n'est capturé. Aucun mot de passe de routeur n'est demandé ni enregistré. Le serveur n'écoute que sur 127.0.0.1.
          • Aucun droit administrateur n'est nécessaire : les pings utilisent l'API ICMP de Windows (sans socket brut), le DNS est interrogé par une simple requête UDP, le trafic vient des compteurs de l'interface. Il en faudrait pour attribuer le trafic par programme (capture ETW/pilote) — volontairement non utilisé.
